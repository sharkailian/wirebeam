# dropsend

手机 ⇄ 电脑 的局域网互传工具。电脑上敲一条命令出二维码，手机扫码，浏览器里就能双向传文件、文件夹和文本。

**手机上什么都不用装。**

```
┌── 电脑 ────────────────────────────────┐        ┌── 手机（浏览器）──┐
│  drop serve                            │        │                   │
│    ↓  终端打出二维码 + 6 位 PIN        │  扫码  │  输入 PIN         │
│  HTTP + SSE  （零依赖，Node 24）        │ ◄────► │  选文件/文件夹    │
│    ↓                                   │  WiFi  │  进度条、断点续传 │
│  data/recv/   ← 手机传来的落这里        │        │  文本互传         │
└────────────────────────────────────────┘        └───────────────────┘
```

## 为什么这样设计

| 决策 | 理由 |
|---|---|
| 手机端用浏览器，不做 App | 免安装、免签名、iOS/Android 通吃。代价是受浏览器沙箱限制，所以协议要把"锁屏断连"当成常态而非异常。 |
| 纯局域网直连，不经过任何服务器 | 速度就是 WiFi 的速度（实测千兆/5GHz 下单流 **160 MiB/s**），文件不出内网。 |
| 零运行时依赖 | 只用 Node 内置模块。不需要 `npm install`，可离线跑，也便于日后打包成单个 `.exe`。 |
| 分片 + 位图 + 幂等 | 手机锁屏、切后台、切 WiFi 都会掐断连接。把"已传成功哪些块"持久化在手机 IndexedDB 和电脑状态里，回来能接着传。 |
| SSE 而不是 WebSocket | 进度是服务器→手机单向推送。SSE 原生支持、浏览器自带断线重连，还不用手写握手与分帧。 |
| 二维码带一次性令牌，但 PIN 不进 URL | URL 会留在浏览器历史和截图里。PIN 让用户手输，令牌只负责"知道地址"。 |

## 校验到哪一步（说实话）

- **电脑端**：每个文件落盘前都会算一遍 SHA-256。手机上送 `sha256` 时它必须一致，否则**拒绝落盘并清空该文件的分片状态**；
  没送也照样算并存下来，供你事后核对。
- **手机端**：从电脑下载的文件会按分片重组，但**没有做整文件哈希比对**——
  浏览器端大文件流式哈希要额外实现（WebAssembly 或增量 SHA-256），当前版本没做。
  所以"电脑→手机"的完整性只有分片长度与 HTTP 传输层的保证。
- 两端的测试都用真实哈希比对验证过（见下方验收结果），但那验证的是传输链路，不是手机端的自证。


## 环境要求

- **Node.js ≥ 22.6**（需要原生 TypeScript 类型擦除）。已在 **Node 24.20.0** 上验证。
- 手机与电脑连同一个 WiFi / 同一网段。
- 无需 `npm install`，项目没有第三方依赖。

## 快速开始

```bash
cd dropsend

# 方式一（推荐）：用自带启动器，之后在任意目录都能直接敲 drop
#   把 E:\dsh_project\dropsend 加进 PATH，然后：
drop serve

# 方式二：不配 PATH，直接指定完整路径
E:\dsh_project\dropsend\drop.cmd serve

# 方式三：在项目目录里用 node（注意必须在项目目录内，否则找不到 bin/drop.js）
node bin/drop.js serve
```

启动后终端会打印二维码：

```
# 1) 手机相机扫码 → 打开网页 → 输入电脑上显示的 6 位 PIN
# 2) 手机端选择文件/文件夹即可发送；电脑上的文件用下面的方式推过去
drop send D:\照片\假期
drop clip "在手机上粘贴这段文字"
```

> **两个目录的区别**（`drop.cmd` 刻意这样设计）：
> 数据目录（`data/recv`、状态文件）**始终**是项目目录下的 `data/`，
> 不会因为你在哪个目录敲命令而到处乱放；
> 而你在命令行里传的相对路径，按**你当时所在的目录**解析，符合命令行直觉。

只想临时用一个会话，不想改 PATH：

```powershell
Set-Alias drop "E:\dsh_project\dropsend\drop.cmd"
```

## 命令

| 命令 | 作用 |
|---|---|
| `drop serve` | 启动服务并打印二维码。文件默认落到 `./data/recv/` |
| `drop send <文件或文件夹...>` | 把电脑上的内容推给手机（手机浏览器会立即出现下载卡片） |
| `drop clip "文本"` | 把文本推送到手机 |
| `drop clip -` | 从标准输入读文本推送（可配合管道：`git log \| drop clip -`） |
| `drop clip --pull` | 读取电脑剪贴板并推送到手机 |
| `drop list` | 列出最近的传输任务 |
| `drop list --json` | 以 JSON 输出（便于脚本处理） |
| `drop selfcheck` | 环境自检 + 本机回环端到端验证 |
### serve 的常用选项

```bash
drop serve --dir D:\接收入口        # 改接收目录
drop serve --port 9000             # 改端口（被占用会自动顺延）
drop serve --host-ip 192.168.1.7   # 多网卡时手动指定二维码里的地址
drop serve --loopback              # 只监听 127.0.0.1（本机调试）
drop serve --no-clipboard          # 收到文本时不写入本机剪贴板
drop serve --verbose               # 打印每个请求
```

## 接收目录结构

```
data/
  recv/                            ← 手机传来的东西落在这里
    单文件.txt                      ← 单个文件直接落根目录
    我的照片/                       ← 文件夹/多选：整体放进以批次名命名的目录
      子目录/深文件.bin
      顶层文件.bin
      空目录/                       ← 空目录也会被还原
  .state/
    runtime.json                   ← 运行中的服务信息（含仅限本机的控制令牌）
    transfers.json                 ← 状态快照
    journal.jsonl                  ← 追加式日志，断电可恢复
    chunks/<任务号>/<文件号>.part    ← 未传完的分片，重启后仍可续传
```

同名文件不会被覆盖，会自动变成 `文件 (1).txt`。

## 安全模型

这个工具的能力是"让手机往电脑写文件"，所以边界必须说清楚：

- **配对**：二维码里带一次性令牌（10 分钟有效，用过即换），进页面后必须手输 6 位 PIN。
  PIN 连续错 8 次作废当前配对窗口，避免在线暴力枚举。
- **会话**：配对成功后发放 32 字节随机令牌，写入 `HttpOnly` + `SameSite=Lax` Cookie，有效期 24 小时。
- **路径防护**：所有来自手机的相对路径都要过 `src/lib/fs-safety.ts`——
  拒绝 `..` 穿越、绝对路径、UNC 路径、盘符、Windows 保留设备名（`CON`/`NUL`/`COM1`…）、
  非法字符、尾部点与空格、全角字符伪装；超长路径直接拒绝。
  **没有任何文件能落到接收目录之外。**
- **本机控制令牌**：`drop send` / `drop clip` 用 `runtime.json` 里的令牌证明"我是本机 CLI"。
  服务端只在请求确实来自 `127.0.0.1` 时才接受它，手机拿不到也无法使用。
- **落盘原子性**：分片先写 `.part`，整文件哈希校验通过后才改名为最终文件。
  **接收目录里永远不会出现半截文件。**

未覆盖的范围（有意为之）：不做 TLS，因此同一 WiFi 下的其他设备理论上可以抓包看到明文。
需要更强保证时请用可信网络，或等待后续的加密传输选项。

## 已知限制

- **必须在同一局域网**。公司/酒店 WiFi 的 AP 隔离会阻止手机访问电脑——这是这类工具最常见的失败原因。
  判断方法：手机连不上时先在手机浏览器打开 `http://<电脑IP>:<端口>/`，若超时基本就是 AP 隔离或防火墙。
- **首次运行可能需要放行防火墙**。`drop serve` 会尝试自动添加规则；失败时会打印一条需要管理员权限执行的命令。
- **浏览器拖拽不带目录结构**。要保留层级请用"选择文件夹"按钮（依赖 `webkitdirectory`）。
- **iOS 后台限制**：上传过程中锁屏会中断连接。协议支持续传（服务重启也能续），但需要把页面重新切到前台。
- **剪贴板同步依赖 PowerShell**（Windows），且有两个已知边界：
  - 本机实测 `Set-Clipboard -Path`（读临时文件）**会静默写入空内容**，因此实现改用
    `Set-Clipboard -Value` 把文本内联进 `-EncodedCommand`。这条路径实测可靠。
  - 内联受 Windows 命令行长度限制。实测边界：11 500 字符通过、12 000 字符报 `ENAMETOOLONG`，
    因此阈值取 **8 000 字符**。更长的文本会依次尝试文件方式与 `clip.exe`；
    若最终仍写不进系统剪贴板，**文本本身照常完整保存在服务端与手机网页里**，
    只是不会出现在电脑的 `Ctrl+V` 中——这时会在终端明确提示，而不是假装成功。
  - 在禁止子进程通信的受限环境里，剪贴板同步不可用，用 `drop selfcheck` 可以确认。

### 为什么二维码要单独用一个独立解码器验证

二维码是**唯一的配对入口**，而它的错误方式很隐蔽：一个"自洽但不符合规范"的码，
自家解码器能读通、手机相机却读不出来。所以 `test/lib/qrdec.mjs` 是一份**独立实现**的
译码器（不复用编码器任何内部结构），走真正的译码流程：定位 → BCH 校验格式信息 →
反掩码 → 按规范逆交织 → **用 GF(256) 多项式求值验证 Reed-Solomon 伴随式全为零** → 解析数据流。

伴随式全零是最强的单项证据：它证明纠错码字是按规范算出来的。

`test/qr-crosscheck.test.ts` 更进一步：它用另一份独立实现 **`test/lib/qrbuild.mjs`**
从数据码字重新交织、重算纠错、重新布局、重新掩码，造出一个完整符号，
然后要求它与编码器的输出**逐模块完全相同**。这一项能抓到"两边犯同一个错"
那类自洽型缺陷——如果编码器在交织或矩阵布局上偏离规范，自家解码器可能照样读通，
但另一套代码不可能对得上。

这两份独立实现由独立审计方编写，并先对其自身做过验证（基线输出见
`test/lib/qr-audit-baseline.txt`）。审计结论：160 个 (版本, 纠错等级) 点全部与几何推导的
容量表一致，**每个符号的每个块的 Reed-Solomon 伴随式全为零**，
3435/3435 个纠错块与审计方独立 RS 编码器的结果逐字节相同，
终端渲染重建后的矩阵与 `encodeQr()` 输出**0 个模块差异**。

这套验证确实抓到了真 bug：

- 编码器的 `v8-H` 纠错块数被写成 5（正确是 6），会产出"自己的解码器读得通、规范却不对"的
  二维码，**只有独立的容量表才能发现**；
- 规则 4 的惩罚值算成了规范的两倍；
- 规则 3 的 4 模块窗口没有在符号边界截断，导致无法复现官方向量里的掩码；
- 终端渲染的静默区只有 2 个模块（规范要求 ≥4），且奇数行时只在底部补行，
  实测是 **左2/右2/上2/下3** ——现在固定为**左4/右4/上4/下5**，并有测试钉住。

> 审计员明确说明的**未能覆盖**部分，一并如实记录：环境无网络、无第三方二维码库，
> 因此没有与第三方实现交叉验证；解码的是**精确的布尔矩阵，不是照片**，
> 没有经过模糊、透视、打印或摄像头成像链路——"手机相机能扫出来"是从
> 伴随式/BCH/几何证据**推断**出来的，不是摄像头实测。

实测结果（Node 24.20.0，本机回环）：

| 项目 | 结果 |
|---|---|
| 1 GiB 单文件传输 + SHA-256 比对 | ✅ 一致，3.9s，**262 MiB/s** |
| 断点续传（传 2/5 块后中断 → 查位图 → 补传） | ✅ 最终哈希一致 |
| 文件夹传输（中文名 + 嵌套目录 + 空目录） | ✅ 结构与内容完整还原，无重复嵌套 |
| 电脑→手机推送（分片重组 + 显式确认） | ✅ 分片重组一致，确认后才标记完成 |
| 恶意相对路径（4 种攻击） | ✅ 全部 400 拒绝，无文件逃逸 |
| 服务重启后续传（会话存活 + 位图不丢 + 孤儿分片不误清） | ✅ 逐字节一致 |
| 二维码（独立解码器 + 独立构造器逐模块比对） | ✅ 配对 URL 逐字节一致；重建符号 0 个模块差异 |
